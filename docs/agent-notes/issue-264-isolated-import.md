# Install libraries imported by the runtime bundle

The Cordis bundle's `lib/index.js` imports `@deepseek-ai/schemastery` and `@earendil-works/pi-ai` at module load. Alpha 4.46 declared both only as peers, so a profile that supplied the DSH host packages but not these two libraries could fail before plugin activation. Resolving an older host-level schemastery also exposed a `.volatile()` method mismatch. A profile-local dependency workaround confirmed that the missing libraries, not credentials or plugin configuration, caused the reported failure.

The plugin now declares exact, plugin-owned runtime dependencies for schemastery `3.18.4` and pi-ai `0.85.1`. DSH, Cordis, and React remain peers because they are host-owned APIs whose module identity must remain shared. The runtime bundle continues to externalize these imports; the package manager installs the two direct dependencies beside the plugin instead of relying on incidental profile hoisting.

`check:isolated-import` copies the built package into a disposable profile, exposes the declared host peers except these two libraries, links only the plugin's declared direct dependencies beside its package, and imports the real built entry point in a fresh Node process. Before the manifest change, the same check failed on missing schemastery. The DSH install matrix exercises the packed artifact with the declared host version and remains the compatibility gate; the isolated import check does not claim a real-account or Windows acceptance run.

> **Superseded for pi-ai (current build):** pi-ai is no longer externalized. `tsdown.config.ts` now lists `@earendil-works/pi-ai` (and its transitive `partial-json`) in `alwaysBundle`, so the entry bundle embeds the plugin-owned pi-ai `1.1.0` and makes no bare `import` of pi-ai. Reason: DSH hosts may resolve a different pi-ai (for example `1.0.2`), and the plugin must work regardless of which one is installed. The `dependencies` entry for pi-ai is kept so the compatibility manifest and install still pin the exact version. Schemastery and the DSH/Cordis/React peers remain externalized as described above.

> **Superseded for pi-ai (0.2.0-alpha.4, adapter-owned pi-ai):** the bundled-copy strategy is reversed. The host build substitutes a bridge for the source/standalone pi-ai entry. It resolves the actual DSH adapter first, then locates that adapter's physical pi-ai dependency and imports its public ESM exports. This avoids both bundled duplicates and profile-hoisted duplicates in directory/link or tarball/file layouts. The pi-ai peer is optional so installing this plugin does not require an automatic profile copy; `1.2.0` remains the tested baseline, not an exact-version runtime gate. The optional peer has no upper version bound (`>=1.2.0`); newer host versions are allowed while the required public exports/functions remain available. Diagnostics retain an unverified label without refusing explicit probes. Concrete missing APIs fail with an actionable error and never trigger fallback to a plugin-owned copy. `doctor --install-anchor` reads pi-ai from the selected host adapter's graph, including nested dependencies. The isolated-import check provides no profile pi-ai peer and plants a poisoned same-version copy beside the plugin: the built entry must still load through the adapter-owned package. Pack checks reject bare pi-ai imports in the host entry. The standalone CLI (`lib/bin.js`) still bundles pi-ai at build time because it runs outside any host. Schemastery remains a plugin-owned externalized dependency. Local synthetic checks do not replace the exact-version installed-host matrix or live-account acceptance.
